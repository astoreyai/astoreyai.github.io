Keeping API keys out of AI agents

Aaron W. Storey, October 2026

I run coding agents on my own workstation every day, and they need API keys. The usual answer is an .env file or an exported variable. That puts the key in the agent’s environment, where one env call, one debug log, or one prompt-injected instruction can copy it out. I wanted the agent to be able to use a key without ever holding it. This note describes what I tested, what I built, and what I found along the way. The code is public: github.com/astoreyai/agent-keyring.

Three tools, tested by hand

On October 16 I installed three open-source secret managers aimed at AI agents and tried to get a key out of each one the way a misbehaving agent would.

  • secretctl encrypts at rest and redacts secrets from command output. The redaction is an exact string match. Piping the key through base64 or rev printed it in a form that was trivially reversible. Its MCP server also needs the master password in its own config file.
  • agent-secrets keeps its age identity file next to the encrypted store. That one file decrypted the whole store with no password and no running daemon. Its lease command prints the raw value.
  • agent-vault (Infisical, MIT) never gives the agent the key. The agent sends requests with a placeholder through a local HTTPS proxy, and the proxy attaches the real credential on the way out, scoped to one host.

The lesson from the first two is that redacting output is not a boundary. If the key is anywhere the agent can read, the agent can transform it and carry it out. I built on agent-vault because its design keeps the key out of the agent’s reach entirely.

What keyring adds

keyring is agent-vault v0.40.0 with twenty local patches and a small launcher, collar, that runs agents in a container whose only way out is the proxy. Each patch fixes a problem found by testing or review, and each has a test that was shown to fail with the fix removed. A few of the problems, all in the upstream release:

  • Plaintext injection. A request to http://host:443/ got the real credential attached and sent without TLS.
  • Token on the command line. The agent’s token was passed on the docker run command line, where every local user can read it in /proc.
  • Self-approved exfiltration. An agent could file a proposal pointing a key at a host it controlled. If the owner approved it, the key went there. keyring refuses proposals.
  • DNS out of a locked container. The container firewall allowed loopback, and docker’s embedded resolver listens on loopback, so DNS was an open outbound channel from a container that was supposed to have one exit.
  • A credential name as a shell hook. A credential named BASH_ENV became an environment variable in the container’s root entrypoint, which would have run a file from the agent’s workspace as root before the firewall came up.

A red-team pass also found that in the documented workflow, a child process could read the operator’s session file and fetch any credential. keyring runs agents with a proxy-only token instead, so no operator session sits on disk.

Limits

The key protection is only as strong as the boundary around the agent. On a workstation where the owner account has passwordless sudo and docker access, an agent running directly as that account can reach anything, including the vault. That is why collar runs agents in a container by default.

Every review so far was automated, done by AI models in several rounds. No human has audited this code. The security audit lists each finding, what was fixed, what was accepted and why, and what has never been looked at. I would welcome a human reviewer.

What I take from it

Agents change the threat model for ordinary credentials. A key in an environment variable used to be exposed mainly to the programs I chose to run. Now it is exposed to a program that takes instructions from web pages, issues and files it reads. The agent should hold a capability to use a key, scoped to one destination, never the key itself, and the path out of its sandbox has to be one path, DNS included.
